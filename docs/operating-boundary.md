# Operating boundary

This document describes the first release boundary for the generated WebMCP package. The browser page remains the action runtime: generated modules call and await `document.modelContext.registerTool()` directly, recording rejected registrations as compatibility or permission diagnostics, while a self-hosted or platform-hosted server serves static files only.

## Understanding

The local CLI observes ordinary rendered HTML, visible text, controls, links, forms, and optional screenshots through Playwright. Text capture limits count Unicode code points so truncation cannot produce invalid JSON from half of an emoji or another supplementary character. A bounded frontier chooses representative pages instead of enumerating every URL or query value. Deterministic scoring uses novelty, uncovered functionality, uncertainty reduction, estimated cost, and access risk. A local Codex/agent may propose labels, actions, summaries, and a ranking of discovered candidates; the explorer accepts only known candidate URLs, ignores duplicate or malformed suggestions, and puts omitted candidates back under deterministic ranking. Selected observations retain their reason, score, and scoring factors for review. Agent output is stored as a proposal until evidence and merchant review resolve it. `discover --out site.json` writes the plain model at that path, with the human-readable report, compact agent input, and agent prompt in sibling files; this keeps the artifact directly consumable by `apply-proposal` and `compile`.

The configured merchant origin is the default boundary. A temporary understanding origin may be supplied for a linked page or resource that is necessary to understand the merchant flow; each distinct explicit origin expands the default origin budget by one, while an explicit `--origins` value stays a hard cap. The finite budget accepts up to 500 origins so a site with several necessary external services can be understood without removing the bound. When that cap is reached, candidates on new origins remain in the unvisited frontier while eligible candidates on already visited origins can still be explored. A navigation attempt consumes its origin allowance even when the site blocks it. Reports distinguish origins allowed for understanding from origins with recorded observations. Page families record the exact origin where they were observed. Understanding access is recorded separately and never becomes a runtime external-origin allowlist entry automatically. A family on that origin can register tools only after the merchant separately approves the origin in `runtimeExternalOrigins`. Non-HTTP links are excluded from navigation candidates. Recognized challenge pages are recorded as blocked observations; browser navigation exceptions such as connection failures and timeouts are recorded as failed observations. Neither seeds more exploration or counts as observed coverage.

`discover --runtime-external-origin <origin>` records merchant approval for generated tools on an external origin. This permission does not authorize the understanding crawler to visit it; use `--understanding-origin` separately when observation access is needed. Either permission may be recorded without the other.

An origin allowlist entry may be supplied as any explicit HTTP(S) URL, including a subpath, query, or fragment. The CLI parses the URL and stores only its canonical origin, so path-level details never broaden the policy boundary. Credentials and non-HTTP(S) schemes are rejected. This permits a merchant to paste a known page URL while retaining exact origin matching.

Generated page-family matching rejects undeclared query keys by default. When observed site URLs show that extra keys such as campaign or storefront state do not identify a different page family, the reviewed model may list that exact merchant, understanding, or runtime-approved external origin in `relaxedQueryOrigins`. This accepts extra query keys only on the listed origin and keeps page paths and required query keys in force. It is a URL-matching decision, not runtime permission: an external origin still needs separate approval in `runtimeExternalOrigins` before its tools can run.

The `discover` command accepts repeated `--relaxed-query-origin` entries and records them in the reviewable site model. Each entry is canonicalized to an exact HTTP(S) origin and validated against the merchant origin, understanding-origin list, or separately approved runtime external-origin list. This makes the exception visible to the merchant before package compilation; it does not infer runtime approval from an understanding-stage visit or infer URL relaxation from runtime approval.

## Generated package

The package contains a bootstrap module, runtime helpers, one module per reviewed page family, semantic Markdown assets, provenance, a review report, a deterministic manifest, integrity metadata, and merchant integration instructions. `manifest.json` and `metadata.json` list SHA-256 digests for the same payload files; neither lists itself or the other, so verification has no circular hash. The bootstrap checks that the current origin is either the merchant origin or a separately approved runtime external origin, then checks the page family's own origin and URL rules before importing a module. Unsupported pages register no tools. A browser without Chrome's experimental WebMCP API receives a compatibility diagnostic.

Both self-hosted and platform-hosted delivery use this same immutable, versioned file set. The package includes a suggested versioned static path and script tag; a platform host serves those files only and is never used as an action endpoint. Platform deployment itself is an asset-store operation outside the local compiler.

After uploading the generated directory, run `verify-hosted --package <downloaded-directory> --base-url <versioned-static-directory-url>` to validate local payload hashes and compare every hosted asset byte-for-byte with the downloaded copy. The verifier compares raw bytes, avoiding false matches caused by invalid UTF-8 decoding. This command is provider-neutral and read-only: it verifies a URL supplied by the operator and does not select a hosting provider or publish files.

This repository also includes a GitHub Pages workflow for platform-hosted delivery. It publishes only committed files under `site/`, verifies each generated payload hash, and rejects changes to any package version directory already present in the prior `main` revision. Manual workflow runs use the current commit's parent as the comparison point because `workflow_dispatch` has no prior SHA. Publish updates under a new version path. The checked-in `0.1.0` pizza-maker artifact is an infrastructure sample compiled from the original rendered-page observation; it deliberately contains zero executable actions because no candidate action has passed merchant review and validation. It demonstrates static delivery and integrity checks, not usable pizza ordering tools. This repository is public, so its committed source, documentation, and Git history are visible to everyone. Pages must be enabled with GitHub Actions in repository settings; after the workflow succeeds, the package URL is `https://iungens.github.io/agent-walkin-webmcp/webmcp/googlechromelabs-github-io-webmcp/0.1.0/`.

Read, preview, and live-write tools are separate. Read and preview handlers do not submit a business action. A live-write click is confirmed only when reviewed postconditions are observed; a click without a postcondition is reported as unconfirmed.

Action input properties must map one-to-one to uniquely observed native controls. Each binding points to evidence and repeats its selector and control kind, which the model validator checks against the original observation (including an input's type where recorded). Runtime checks the live page control again before use. Read and preview modes validate availability but leave field values untouched; only live-write applies the supplied values and emits `input` and `change` events before dispatching the reviewed control.

## Deferred scope

Login, password entry, account recovery, authenticated areas, and credential handling are deliberately deferred. The first release also does not add a connector, facade, MCP server, server-side action endpoint, hosted merchant review UI, or alert delivery workflow.

The local reasoning adapter receives a compact evidence bundle and returns a schema-checked proposal. It may relabel observed page families, cite existing controls, summarize observed material, and rank discovered frontier URLs. Unknown evidence, page families, or URLs are rejected or downgraded for review; agent output never grants merchant approval. Semantic Markdown separates observed facts, agent summaries, and action meaning, and each material section retains its source URL and evidence identifiers. Password and likely authentication pages are marked deferred without serializing their controls or field values.

## Browser validation

The API smoke test used Chrome `156.0.8078.80` with `--enable-experimental-web-platform-features` against a locally served test page. It checked that `document.modelContext.registerTool()` existed and accepted a minimal registration. Automated package tests separately cover missing-API diagnostics, duplicate registration, asynchronous registration rejection and retry, page-family dispatch, and generated package loading from a local static server. This records one experimental Chrome build; it does not establish compatibility with other Chrome versions, agents, or a stable WebMCP API revision.

Four bounded ordinary-page discovery reports are stored under `artifacts/goal-verification-20261104/`. The Grundig and pizza-maker reports were generated from rendered page observations without reading their existing WebMCP definitions. The Phiphipirate report covers the requested `/en` URL. Caribou Coffee encountered an automated-access challenge, so the report records blocked/partial coverage. These reports are discovery evidence only: no site-specific action has passed browser validation yet, and the reports do not establish full site coverage.
